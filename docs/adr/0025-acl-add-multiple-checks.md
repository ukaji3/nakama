# ADR 0025: acl add は 2 つのチェックサイトに 3 回ずつ問い合わせ、見つかった IP をすべて登録する

- Status: Accepted
- Date: 2026-10-23
- Issue: [#104](https://github.com/ukaji3/nakama/issues/104)
- 関連: ADR 0002 (WAF の IP set による許可)、ADR 0015 (プロキシの解決)

## Context

`nakama aws acl add` を引数なしで実行すると、接続元のグローバル IP を調べて許可リスト (WAF の IP set) に登録する。これまでは `https://checkip.amazonaws.com/` に 1 回だけ問い合わせ、その 1 つを登録していた。

出口を冗長化しているネットワークでは、接続ごとに違う出口が選ばれることがある (複数のプロキシへの振り分けや、複数のアドレスを持つ NAT など)。ブラウザはどの出口からも出るので、1 回の問い合わせで見えた出口だけを登録すると、ほかの出口から来た通信が 403 になる。利用者から、ifconfig.io (`curl -4 https://ifconfig.io/` のような問い合わせ) も使い、チェックサイトを 3 回実行して、重複を除いた IP を登録してほしいという要望があった。

調べたこと (この Ubuntu。直接接続、デュアルスタックの回線):

- ifconfig.io は IPv4 (A) と IPv6 (AAAA) の両方のアドレスを持つ。IPv4 を指定しないで問い合わせると IPv6 でつながり、IPv6 のアドレスが返る。checkip.amazonaws.com は IPv4 のアドレスしか持たない。
- `https://ifconfig.io/` は User-Agent を見て、ブラウザなどには HTML を返す (User-Agent が無いと HTML)。`https://ifconfig.io/ip` は User-Agent に関係なく、IP だけを平文で返す。
- checkip.amazonaws.com は、リクエストに X-Forwarded-For があると、その先頭の値をそのまま返す (プライベートアドレスも返す)。ifconfig.io は X-Forwarded-For を見ない。

## Decision

- **チェックサイト**: `https://checkip.amazonaws.com/` と `https://ifconfig.io/ip` (`internal/awsx` の `ipCheckSites`)。
- **回数**: それぞれに 3 回ずつ (計 6 回)、同時に問い合わせる (`DetectPublicIPv4s`)。同時にするのは、待ち時間を 1 回分 (最長 5 秒) に抑えるため。
- **毎回新しい接続**: keep-alive を切る (`DisableKeepAlives`)。HTTP/2 の接続も 1 回ごとになる。接続を使い回すと、接続ごとに出口を選ぶネットワークでも 1 つの出口しか見えないため。プロキシを経由するときも、毎回 CONNECT からやり直す。
- **IPv4 での接続**: チェックサイトへ直接つなぐときは、`curl -4` と同じく IPv4 で接続する (`tcp4`)。プロキシへの接続はこれまでどおりにする。プロキシがチェックサイトへどちらのアドレスでつなぐかは、nakama には決められない。
- **答えの検査**: 公開の IPv4 アドレスだけを受け付ける。IPv6、プライベートアドレス、ループバック、リンクローカル、CGNAT (100.64.0.0/10)、マルチキャストなど、IP として読めないもの (HTML など) は、その回の失敗とする。TLS を中継するプロキシが X-Forwarded-For を付けると checkip が社内の IP を返すため、それを登録しないようにする。
- **登録**: 見つかった IPv4 アドレスの重複を除き、それぞれを /32 として、1 回の `UpdateIPSet` で足す (既にあるものは足さない)。追加日時はすべて更新する。
- **失敗**: 1 つでも見つかれば登録する。失敗した問い合わせがあれば、サイトごとに「何回中何回失敗したか」と最初のエラーを警告し、出口を取りこぼしたかもしれないことを伝える。全部失敗したら、何も登録せずにエラーにする。
- **出力**: 1 つなら今までと同じ (`added: X`、JSON は `{"added": "X"}`)。複数なら 1 行ずつ出し、JSON は配列にする (`acl delete` の複数指定と同じ形)。
- **`acl delete all --keep-mine`**: 同じ検出を使い、見つかったどれかの IP を含むエントリを残す。1 つしか調べないと、`acl add` が登録したほかの出口のエントリを消してしまう。結果の JSON には `my_ips` (全部) を加え、`my_ip` (先頭) も残す。
- **`open` の警告と `doctor`**: 今までどおり checkip に 1 回だけ問い合わせる (`PublicIPv4`)。登録が漏れていないかの目安には足り、速い。

## Consequences

- 接続ごとに出口が変わるネットワークでも、問い合わせで見えた出口はすべて登録される。ただし、6 回で全部の出口が見える保証は無い。出口の数が多いときや、時間や日によって出口が切り替わるときは、CIDR での登録 (`acl add 203.0.113.0/24`) や、`acl add` のやり直しが必要になる。
- 出口が 1 つのネットワークでは、結果は今までと同じ (1 つの IP)。
- AWS 以外のサイト (ifconfig.io) の答えも許可リストに入る。ifconfig.io (または TLS を中継する経路) が嘘の IP を返せば、その IP が登録される。HTTPS で接続し、公開の IPv4 以外は受け付けないが、公開の IP であれば区別できない。登録した IP は `added:` に表示される。
- IPv6 でチェックサイトにつなぐプロキシの下では、ifconfig.io は IPv6 を返すので、その回は失敗として警告される (checkip の答えは使える)。
- 問い合わせは 1 回から 6 回に増える。同時に行うので、待ち時間はほぼ変わらない (この Ubuntu で 0.5 秒)。

## Alternatives considered

- **`https://ifconfig.io/` (末尾の `/`)**: 依頼の例のとおりだが、User-Agent によって HTML を返す。Go の既定の User-Agent では平文が返るものの、それに頼ることになる。`/ip` は ifconfig.io のページが案内している平文の API である。
- **順番に 3 巡する**: 依頼の「3 回実行」に近い形だが、サイトが応答しないと待ち時間が最長 15 秒に延びる。同時でも 1 回ごとに新しい接続になるので、出口の見え方は変わらない。
- **両方のサイトが同じ IP を答えたときだけ登録する**: 嘘の IP は防げるが、出口ごとに答えが違うネットワークでは、登録すべき IP を落とすことになり、目的に反する。
- **プロキシへの接続も IPv4 にする (`curl -4` と同じ)**: プロキシが IPv6 でしかつながらない環境で、これまで動いていたものが動かなくなる。プロキシへの接続の種類は、チェックサイトが見るアドレスに関係しない。
- **ifconfig.io の IPv4 専用のホスト名を使う**: ページに案内が無く、使えると確かめられなかった。
