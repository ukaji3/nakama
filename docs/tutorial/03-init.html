第 3 章 土台を用意する

開発環境を作る前に、その置き場所となるネットワークなどの共通部分を用意します。この作業は AWS アカウントに 1 回だけで、あとは何台作っても共有されます。

1. init で土台を作る

PowerShell で実行

nakama aws init

数分かかります。進行状況が順に表示され、エラーが出ずに終われば成功です。うまく終わったかは次で確認できます。

nakama aws doctor

capability: init の行が ok で、credentials も ok なら問題ありません。途中でエラーになった場合は、そのまま nakama aws init をもう一度実行してください (できているところは飛ばされます)。

作られるものは次のとおりです (すでにあるものは作り直さずそのまま使います)。

作られるもの役割
VPC とサブネットAWS の中に用意する専用のネットワーク区画。開発環境は外から直接触れない「プライベート」側に置かれます
インターネットゲートウェイとルートテーブル外向きの通信経路の設定 (触る必要はありません)
NAT インスタンス開発環境が外部と通信する (ソフトのダウンロードなど) ための小さな中継サーバー
IAM ロールとインスタンスプロファイル開発環境が AWS の機能 (SSM 経由の接続など) を使うための権限 (触る必要はありません)
WAF (Web ACL と IP セット)正面玄関の門番。許可した IP からのアクセスだけ通します
SSM パラメータ作ったリソースの ID などの控え (nakama が次回以降参照します)
何度実行しても大丈夫です

init は冪等です。すでに nakama が作ったリソースがあれば、それを再利用します。「途中で失敗した」「設定が合っているか不安」というときは、もう一度実行して構いません。

最後に NAT インスタンスを点検します

init は最後に、NAT インスタンスが通信を中継できているかを確かめます。結果は表示の nat forwarding の行に出ます (ok なら正常、repaired なら壊れていたものを直したという意味です)。直すときは、セキュリティ更新もあわせて入れるので、数分かかります。NAT インスタンスが停止中なら点検のために起動し、終わったら停止に戻します。

直せなかった場合、init はエラーで終わります。もう一度 init を実行してください。

以前の nakama から移行する場合の注意

過去のバージョンの nakama が作った NAT ゲートウェイが残っている場合、init はそれを削除し、割り当てられていた固定 IP (Elastic IP) を解放します。これは、より安価な NAT インスタンスへ移行するためです。通信が途切れないように、先に新しい経路へ切り替えてから削除する順序で行われます。

初めて nakama を使う場合は、この動作は起こりません。

リージョンは東京固定です

nakama は ap-northeast-1 (東京) を前提に作られています。他のリージョンを指定するオプションはありません (使うデータセンターの区画も自動で決まるので、気にしなくて構いません)。

2. 自分の IP を許可する

ブラウザで開発環境を開くには、あなたの接続元 IP アドレスを門番 (WAF) に登録します。登録していない IP からは、正面玄関で拒否されます (403 エラー)。

PowerShell で実行 (いまの接続元 IP を自動で調べて登録します)

nakama aws acl add

登録できたかは acl list で確認できます。IP を明示したい場合や、まとまった範囲を許可したい場合は引数で渡します。

nakama aws acl add 203.0.113.10          # 1 つの IP (自動で /32 が付きます)
nakama aws acl add 203.0.113.0/24        # 範囲で指定 (会社の出口が複数ある場合など)
nakama aws acl list                      # 登録済みの一覧
nakama aws acl delete 203.0.113.10/32    # 削除 (複数を並べてまとめて消すこともできます)

acl list は次のように表示されます。

CIDR                  ADDED_AT
203.0.113.10/32       2026-09-13T00:12:04Z
IP アドレスは変わります

自宅の回線は再接続で IP が変わることがあり、会社のネットワークは出口が複数あって日によって変わることもあります。「昨日は開けたのに今日は 403 になる」ときは、まず nakama aws acl add をもう一度実行してください。

使わなくなった IP は acl delete で消しておくと安全です。

たまった IP をまとめて消す

IP を追加し続けると、もう使っていない IP が許可リストに残ります。acl delete all で一度に消せます。

nakama aws acl delete all --keep-mine    # いまの自分の IP を含むものだけ残して、ほかを消す
nakama aws acl delete all                # すべて消す

どちらも、消す一覧を表示して確認を求めます。y と入力して Enter で実行します (--yes で確認を省けます)。

acl delete all は自分も締め出します

すべて消すと、どの開発環境 (Kiro Crew の画面も含む) も、あなたを含むすべてのブラウザに 403 を返します。使い続けるなら --keep-mine を付けるか、消した後に nakama aws acl add で登録し直してください。connect / ssh / tunnel は許可リストを使わないので、影響を受けません。

許可が要るのはブラウザからのアクセスだけ

connect / ssh / tunnel は SSM 経由なので、IP の許可は不要です (AWS の権限で守られます)。IP 許可が必要なのは nakama aws open でブラウザから開く場合だけです。第 5 章で詳しく扱います。

広すぎる範囲を登録しないでください

0.0.0.0/0 のような「どこからでも」に相当する範囲を登録すると、門番の意味がなくなります。開発環境にはパスワードもかかっていますが、許可 IP は必要最小限にしてください。

3. 料金の考え方

nakama が作るリソースには AWS の料金がかかります。金額はリージョンや使い方で変わるため、実際の見積もりは AWS 料金計算ツール や AWS コンソールの請求画面で確認してください。 ここでは「どこにお金がかかるか」の構造だけを説明します。

対象いつ課金されるか
開発環境の EC2 インスタンス起動している時間だけ。停止すればかかりません
ディスク (EBS)作ってある間ずっと。停止中も保管料がかかります (中身を保つため)
NAT インスタンス開発環境が 1 台でも起動している時間だけ (自動で連動します)。ただし init の直後は起動した状態で作られ、次に stop / delete などで電源が見直されるまで動き続けます
CloudFront通信量とリクエスト数に応じて
WAFWeb ACL が存在する間、時間割りの基本料金 + リクエスト数 (AWS WAF の料金)
バックアップ (スナップショット)保管している容量に応じて。世代を増やすほど増えます
お金を抑えるコツ
  • 作業が終わったら nakama aws stop <名前> で止める (中身は残ります)
  • 使わない環境は nakama aws delete <名前> で削除する (中身も消えるので、必要なものは先にバックアップか git へ)
  • バックアップの世代を --keep で制限する (第 6 章)
  • 大きなインスタンスは必要なときだけにして、ふだんは小さいものに戻す (nakama aws edit --instance-type)
完全にゼロにはなりません

すべて停止しても、次の 3 つは残ります (いずれも小さな額ですが、ゼロではありません)。

  1. 各環境のディスク保管料
  2. WAF の Web ACL の基本料金 (時間割り)
  3. NAT インスタンスの小さなディスクの保管料

土台まで含めて消すコマンドはありません。完全に止めるには、各環境を nakama aws delete で削除したうえで、AWS コンソールから名前が nakama- で始まるリソース (WAF の Web ACL と IP セット、NAT インスタンス、VPC、IAM ロール、SSM パラメータ) を削除します。判断に迷う場合は AWS の管理者に依頼してください。
